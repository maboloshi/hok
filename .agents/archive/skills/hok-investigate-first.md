用户 2026-09-12 明确要求：**未来先调研、报告，等确认再动手。** 默认流程 =
**调研 → 报告（含证据与选项）→ 等用户明确确认 → 才实现/提交**。不得「边查边改、先做后报」。

## 触发范围
- **需要先报告**：新功能、行为/显示变更、性能优化、重构、去重、依赖或架构决策（含「要不要引入外部工具/换实现」）。
- **不需要**：纯问答、只读排查、用户已明确下达「直接改/修好/提交」指令的任务、明显的同类小修（错别字、注释）。
- 判断不了就**先问一句**，不要用「我觉得这显然是 bug」当许可。

## 报告应包含（够用户拍板即可，不冗长）
1. **现象与复现**：具体命令、期望 vs 实际；
2. **证据/实测**：release 数据、官方源码对照（`D:\App\github项目\Scoop\Scoop\libexec|lib`）、file:line；
3. **候选方案与代价**：含「不改」这一项，写清各自的架构/依赖/可维护性影响；
4. **推荐方案 + 影响面**：要动哪些文件、是否新增依赖/间接层、提交怎么拆；
5. **明确请求确认的点**（一次性问清，别挤牙膏）。

## 反面教训（2026-09-12，本规则来源）
- `info -v 性能`：先按「-v 独有路径慢」的假设动手，实测才发现慢点是**两个模式共用**的 git 历史查询（见 `.agents/docs/devlog/2026-09-12-info-git-history-rewrite.md`）；
- 中途自行引入「外部 git CLI 优先」并做成实现，被用户否掉（**本仓不引入外部 git**）→ 白写一轮；改写回 libgit2-only 后仍然拿到了 1.69s → 0.63s。
- 结论：**选型与范围属于用户决策，不属于实现细节**；先给出对照数据让用户拍板，比先写出来再回退便宜得多。

## 与相邻规则的关系
- 本 skill 管「**动手前**的确认门」；[[hok-proactive-review]] 管「**提交前**的 review 门」。两道门都要过：未报告不开工，未 review 不提交。
- 收尾的确定性环节（fmt/clippy/test 本地闭环、只看退出码）见 [[hok-rust-gate-practice]] / 全局 `rust-deterministic-gate`；本 skill 不改变它们的节奏。
