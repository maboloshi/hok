# 0.6.0 审计 P2 口径更正与清单历史索引调研草稿

> 2026-10-03 ｜ 提交 `89864c0` ｜ worktree 主树 ｜ 分支 `refactor/edition-2024`

## 做了什么

**① 更正 `upstream-0.6.0-impact-2026-10.md` 的 P2 口径（上一轮写过头）。**
原文说 `hok install app@<旧版本>`「对 HEAD 中已不存在的版本无解」——错。该用法**本来就支持**：
版本不等时跑 autoupdate 重建（`manifest_source.rs:422-479` → `checkver.rs:1035-1131`，替换 `$version` 后重算 hash，
产物落 `<root>/workspace/<app>.json`），官方 0.5.3 同此。0.6.0 三级链的真实意图是**在"重建不出"时按版本号找回原文**
（模板改过结构 / 产物改过名 / URL 规则变过 / 无 `autoupdate` 段）。同时把 `198818ae` 的官方语义写准：
不是"升级 pin"，而是 `-f` 时**丢掉 pin 重解析**（`$null -eq $bucket -and $url` 一个判据覆盖 URL 安装与生成清单两种来源）。
§1 补 P0 尾巴（版本枚举仍按 mtime）、§4 三条 P3 按 `4168ba8` 实际改动改为已对齐。

**② 三点实测澄清（§3.2）。**
- sqlite 缓存**优先它只为快**：`app` 表主键 `(name, version, bucket)` 且存整份 manifest，结构上能当原文提供层，
  但内容是"扫过的版本"（本机 51 MB / 22311 行，7zip 只有一行）而非完整历史。
- 提交名约定**帮不到查询**：上游 pickaxe 查文件内容（`-G`），实测换成 `--grep` 反而更慢（1229 ms vs 976 ms）。
- 「git2 有问题」要收窄为能力缺口：`blob_at`/`last_commit_for_file`（`internal/git.rs:365-421`）已有且便宜；
  缺的是内容搜索与 `--follow`。且上游 `Invoke-Git` 走原生 git，hok 走 libgit2 所以连它的进度显示都拿不到。

**③ 新增调研草稿 `research/manifest-history-index.md`（`git 库 → 索引库`）。**
定下四点：只存 `(bucket, app, version) → blob_oid` 不存文本（20–30 MB vs 300–400 MB）；同库新表
`hok_manifest_history`（基线 `hok_manifest_sync` 已在同库，拆库会漂移），且**不跟 `use_sqlite_cache` 门控**；
构建由 git2 `diff_manifest_changes` 驱动（**绕开 pickaxe**），增量按 `UpdateChanges` 走父链；
并行只对"提取/解析"那一段（按 app 切、每线程自开 `Repository`），走历史那一段靠算法不靠线程。
未定项已列进草稿 §4（重命名、是否接入 `@version`、引擎形态、是否要开关）。

## 为什么值得记

一次"看起来是缺功能"的对标，实际是**缺一条兜底**；不先核准就会把"能用"判成"不能用"，
进而把排期和优先级都放错位置。教训：对标记完之前先跑一次真实路径（或至少据生成物反推），
别只读调用链就下"无解"结论。
