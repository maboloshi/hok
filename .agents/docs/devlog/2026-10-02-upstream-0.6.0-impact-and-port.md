## 落地

- **P0 元数据文件名**（`03f7ee2`，子代理 A）：官方 0.6.0 写 `scoop-manifest.json` / `scoop-install.json` 并
  「新名优先、旧名回落」，hok 只写只读旧名 ⇒ 官方装的应用对 hok **不可见**（单向破坏）。现改为一套
  `install_info_path` / `installed_manifest_path` / `install_info_mtime` 共享解析，写侧改用新名。
- **P1 checkver GitHub 模式**（`baf4c53` `507aab2`，子代理 B）：4 个上游提交是**一次**行为变更
  （API 模式默认 `$.tag_name` + `[\d.-]` 正则、URL 校验后跳过、`github_solo` 门删除、有脚本时不注入默认 jsonpath），
  外加脚本回退、`originurl` 去 fragment、token 只发 api.github.com。hok 原有 2 条测试锁定的正是**被上游删除的旧行为**。
- **P3 零散项**（`4168ba8`）：两个新 config 键登记、isolated 的 `$bucket` 改空串、`env_set` 每变量一行
  （原只在 `-v` 步骤行可见）、notes 加 `Notes`/`-----` 框架与建议行 DarkYellow、`download` 任一失败 exit 1。
- **P2 未排期**：`use_git_history` + git pull `--tags` + `update -f` pin 提升，已记入审计文档与待办。

## 编排与教训

- 两条子代理分支并行（文件零交集）；P0 先落地后，P1 rebase 到新 tip 并补 zh locale，**两次落地都是
  `--ff-only` + 「逐字节相同」漂移校验**，无 merge commit。
- **P1 落地时命中未跟踪/已跟踪混淆的真实风险**：父会话在 `locales/{en,zh}.yml` 也有未提交改动，而 P1 同改这两个文件。
  按收口检查单第 4 条先 `git stash push -- locales/en.yml locales/zh.yml` → ff → `stash pop`，两套键都完整保留。
  `git merge --ff-only` 对会被覆盖的已跟踪改动本会拒绝，但显式 stash 让冲突面归零。
- **证据纪律见效两处**：① 父会话给 P0 的核对清单要求逐条确认，补出了子代理首轮可能漏掉的 5 个 **mtime 类**读点
  （`list`/`export` 的 `Updated`、`newest_version_dir`、`info`、`broken_package`）；② P3 的 `download` 退出码
  最初只跟踪「已解析但下载失败」，被新增测试 `test_download_apps_one_bad_query_does_not_abort_others` 判红后
  才补上「解析失败的 query」——**上游 5 个失败点都要置位**，静态读码看不出来。
- **自查更正**：父会话把 `script_bucket()` 插在 `run_script` 的文档注释与函数之间，切断了 doc 块并触发
  clippy `doc list item without indentation`；另 `skip_children=true` 的 file-scoped rustfmt 检查**看不到子模块**
  （`script.rs` 的测试模块漏格式化）。两处都改为整文件 `rustfmt --edition 2024 --check` 后修正。
